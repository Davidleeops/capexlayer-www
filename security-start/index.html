01

Make the work finite

Write down what you own.

List each website, hosting account, code repository and database. Include your domain registrar and email account because they can reset access to everything else.

No code access?

Use your provider dashboard to record the runtime, CMS and plugin versions. Ask your developer for a source export and a backup restoration plan.

Before changing anything

Confirm that a recent backup can be restored. Use a staging copy for changes. If you see signs of an active breach, preserve logs and contact your provider's incident support first.

02

Reduce the most consequential exposure

Check who can do what.

  • Enable multifactor authentication for hosting, GitHub, email and the domain registrar. Review recovery methods and remove former users.
  • Check database tables, storage buckets and callable functions for public access. Public content may be intentional; customer records and privileged actions need explicit controls.
  • Keep service credentials on the server. If a private key was exposed, revoke or rotate it at its provider, then update the application and verify it works.
Why database permissions need their own check

A table can have row-level security while a privileged function still permits an unwanted operation. Review tables, views, storage and functions as separate access paths. Do not apply a blanket SQL command you do not understand.

03

Match the warning to your actual software

Update with evidence.

Use the advisory from the software vendor. Match the affected version and required conditions to your installation. Record whether the affected component is actually deployed.

Managed hosting or WordPress

Check the supported PHP/runtime version, CMS, themes and plugins in the provider dashboard. Back up, apply the supported patch, then test login, forms and payments in staging.

A JavaScript repository

From the application folder with its lockfile, run the command below. It reads known dependency advisories and sends package metadata to the registry. It does not fix application permissions.

npm audit --json

Do not run npm audit fix --force as a first response. Review the proposed change, build, test and deploy the verified version.

04

Use a repeatable method

Start with Claude Red's references.

SnailSploit's Claude Red is an MIT-licensed library of security skill instructions. It is free source material, not a one-click scanner. Compatible assistant access, hosting and some testing tools can have separate costs.

Its offensive examples cover advanced techniques. For a first review, read only the API security and reporting references. Use them to organize a bounded review of systems you own.

Hands-on setup: download a pinned reference copy

Run these commands in a new local folder. They download source only. They do not install skills globally or execute the project's installer.

git clone https://github.com/SnailSploit/Claude-Red.git claude-red-reference
cd claude-red-reference
git checkout --detach a8de813edc9f66f60d44cfe42d47750e89d9930b

Open these files in a text editor:

Skills/api/offensive-api-security/SKILL.md
Skills/utility/offensive-reporting/SKILL.md

The pinned revision makes this guide reproducible. Before adopting a newer revision, review its changes and security policy.

A bounded review request

Give this to your developer or a compatible assistant, together with a local source copy and the two references. Confirm your provider's privacy terms before uploading private code. Share no live credentials.

Review only the local repository I provide and systems I explicitly identify as mine. Start read-only. Use the Claude Red API-security and reporting references to organize the review.

Inventory routes, authentication boundaries, database access paths and dependencies. Prioritize publicly reachable privileged actions and relevant critical advisories. Do not exploit production, extract records, brute-force accounts, send messages or change access.

For each finding, show the file or configuration, evidence, affected version and conditions, likely impact, smallest proposed fix, and a safe retest. Separate confirmed facts from hypotheses and unexamined areas. Attribute the original discovery tool correctly. Prepare changes in staging and report what remains unverified.
05

Close the loop

Prove the fix changed behavior.

Before

Record the evidence

Affected version, permission, source location or a safe unauthorized-access result.

Change

Apply the smallest fix

Patch the component or narrow the permission. Keep a recovery path.

After

Retest the live release

Confirm unauthorized requests are denied and intended users can still complete the workflow.

Save the commit or deployment identifier and test date. A passing local build is useful, but the live site may still be running the old version. A denied request can also come from a hosting gate, so check which layer denied it.

06

Spend effort where it changes the risk

Make the next decision clear.

Give your developer or provider one concise record per issue: system, evidence, exposure, owner, proposed fix, verification and due date. Enable dependency alerts and repeat the relevant checks after changes.

If you suspect data theft, unknown administrator accounts or unauthorized payments, escalate to your provider or a qualified incident responder. A checklist does not determine whether a breach occurred.
